# 旧版性能基线

旧版（`legacy/`，Python + FastAPI + SQLite + 官方 MCP SDK，网页是 React + Tiptap）在几个关键场景下的数，给 Rust 重写当要超过的线。
2026-11-18 测的，脚本是 `spikes/baseline/bench.py`，三轮的原始结果在 `spikes/baseline/results-2026-11-18.json`。

## 机器和方法

- **机器**：MacBook（Apple M2，8 核，16 GB），macOS 27.3。旧版跑在 uv 装的 CPython 3.13.3 上，uvicorn 单进程，用了 uvloop + httptools，日志级别 warning（就是 `open-agent-docs serve` 的默认设置）。
  安装用 `uv sync --no-dev --no-editable`，装进单独的 venv，不带测试依赖。
- **机器不空闲**：测的时候别的 Agent 在同一台机器上编译、跑东西，load average 在 8 到 28 之间（8 核）。同一项在三轮之间最多差 2 到 3 倍。
  所以下面的表写的是**三轮里最好那轮的 p50**（p95 也取那一轮），括号里是三轮 p50 的范围。对服务端的接口还记了**服务进程每次请求花的 CPU 时间**（user+sys），它受干扰小一些。
  在空闲的机器上，数大概会贴近或者低于“最好那轮”。
- **怎么跑**：在仓库根目录 `uv run spikes/baseline/bench.py --out <临时目录>`（Python 依赖写在脚本头里，uv 会自己装）。整套约 8 分钟。
  `--only coldstart,pages` 只跑某几项，`--no-frontend` 不开浏览器。
- **客户端**：httpx 从同一台机器发请求，绕开代理。时间是客户端看到的，包含 HTTP 往返（本机约 1 ms）。每个接口先预热 1 次再量，一般量 30 次（数据库那几项量 10 次）。
- **数据**：脚本按固定随机种子生成中英混合的文本：常用词按 Zipf 分布抽，中文句子里夹英文词，英文句子里偶尔夹中文词。
  块的比例大致是：段落 40%，标题 8%，无序列表 18%，有序列表 8%，待办 5%，表格 10%（表头一段、每行一段），代码块 5%，引用 5%。
  词表只有几百个词，常用词在语料里出现得比真实文本更多，所以搜索里“命中太多”那部分的耗时会比真实情况偏高（第 4 条观察细说）。
- **浏览器**：Playwright 自带的 Chromium 159，无头模式，窗口 1320×900，不限速。时间从导航开始算，到 DOM 里出现标记文字、再过一帧为止（页面里用 `performance.now()` 记）。
  “冷”是每次新开一个浏览器上下文（没有缓存），“热”是同一个上下文里再打开一次（静态文件走缓存）。

## 观察：哪里慢，为什么

1. **启动慢、空闲内存大，主要是 import。** `import open_agent_docs.server` 就要 0.5–1.2 s。用 `-X importtime` 按包加总各模块自己的时间：MCP SDK（`mcp` 和 `mcp_types`）约 40%（它在 import 时给好几个协议版本各建一套 pydantic 类型，还顺带 import 了客户端那一半和 opentelemetry），FastAPI 10–17%，pydantic 本身约 10%，旧版自己的代码 5–10%。
   79 MB 的空闲内存基本是解释器加这些库。Rust 单个二进制在这两项上达标不难。

2. **所有请求在一个线程里排队。** 接口都写成 `async def`，里面直接调同步的 `sqlite3`（整个进程共用一个连接），全在事件循环上跑。
   一个慢请求跑的时候，别的请求（包括网页的保存、SSE 推送）都得等：打开 1 万行视图约 400 ms，第一次搜索建索引 2–4 s，`db_add` 到后面每批 1–4 s。
   MCP 端点每个请求还要新建一个 `StreamableHTTPSessionManager`，再起一个 anyio 任务组。

3. **按段改页面，每次都是整页的工作量，还有两处平方级的代码。**
   每次读段（`pagedoc.load`）都把整页 Markdown 重新切一遍段、算一遍每段的指纹，所以 `/blocks` 要 15–20 ms CPU。
   `edit_page` 只改一段也要 53 ms。用 cProfile 看，约 70% 花在两处：一处是 `pagedoc.apply` 结尾的 `gone = [i for i in old if i not in {b["id"] for b in work}]`，每个元素都重建一次集合，1000 段就是约 100 万次操作；
   另一处是 `blocks.join` 用 `text = text + …` 拼 6 万字，每拼一段就把已有的全文复制一遍。
   `rewrite_page` 不走 `apply`，所以整页提交（28 ms）反而比改一段快。另外每次保存都把整页正文写进历史（同一个人 10 分钟内的改动并成一版，但每次照样整页写一遍）。
   网页打开页面时正文要传两遍：`/api/pages/{id}` 里有一份（89 KB），`/blocks` 里又有一份（168 KB）。

4. **搜索每次都先对一遍账，常用词命中的块太多。**
   每次查询先跑 `search.sync()`，把 `search_docs`（1.2 万个块）和 `pages` 两张表整个读出来比 `updated`。一条都命中不了的查询也要 25 ms，这就是下限，已经超过 20 ms 的目标。
   中文按相邻两个字切，查询里的词用 OR 连起来。“数据库 性能”会变成 `"数据" OR "据库" OR "性能"`，常用词能命中 50–90% 的块，BM25 要给所有命中的块打分排序，光 FTS 就要 15–60 ms。
   这个语料词表小，比真实文本命中得多，所以这一部分的数偏悲观；但光是 `sync()` 这一项就已经不达标。
   索引是懒建的：第一次搜索时在请求里同步建，10 万段要 1.6–4 s，这段时间整个服务卡住。改一页之后的下一次搜索要把这一页重新切块、分词（59 ms）。

5. **数据库每次都读整个库，在 Python 里算。**
   不管加不加筛选、排序，打开视图、`db_query` 都是把 1 万行全读出来：每行 `json.loads` 两次（`props`，还有视图根本用不上的 `props_meta`），给每行算公式，再在 Python 里筛选、排序，最后只返回 200 行。所以筛选、排序都是 350–450 ms，彼此差不多。
   cProfile 看：JSON 解析约 45%，算公式约 25%，SQL 约 15%，查每行最后是谁改的（`_last_by`）约 10%。网页往下滚取下一页 200 行时，整套又从头算一遍。
   插入是平方级的：每加一行都要 `count(*)` 一遍这个库有几行（`pages.parent_id` 没有索引，只能全表扫），`_end_pos` 还要把同一个库的行全读出来算新行排在哪，再加上五次 commit 和一份历史快照。
   所以第一批 50 行约 50 ms，到快 1 万行时每批要 1.4–3.8 s。另外旧版限制一个库最多 1 万行（`MAX_ROWS`）。

6. **前端打开页面是一串接力，还有 300 ms 是 React 故意等的。**
   打开一个页面的顺序是：主包（680 KB）→ `/api/bootstrap` → `/api/pages` 和 `/api/pages/{id}` → 先用只读的 Markdown 显示 → 编辑器分块（650 KB）→ `/blocks` → 建编辑器里的文档。
   10 段的短页面也要约 480 ms。看请求时间线，编辑器分块在 110 ms 左右就下载完了，编辑器的节点却到 400 ms 左右才挂上，中间没有长任务。
   这符合 React 19 的 Suspense 回退节流：回退内容显示以后，至少等 300 ms（`FALLBACK_THROTTLE_MS = 300`）才换成真正的内容。这里的回退内容就是那份只读 Markdown。
   1000 段的页面再多出约 260 ms：只读 Markdown 先把 1000 段渲染一遍；编辑器又把每段 Markdown 解析成节点，再一段段序列化回去当基线（`DocSync.bind` 里的 `serializeBlock`）。两次加起来，长任务约 350 ms。
   打字本身问题不大，p50 约 9 ms；但 1000 段页面的 p95 已经到 16–17 ms，有人同时在写时会更差（这次没测）。

## 没测的

- 有人或 Agent 同时在写时的打字延迟、多个客户端并发请求时的吞吐。
- 数据库表格滚动的帧率（旧版没有虚拟滚动，一次 200 行，往下滚再取）。
- 链接卡片（旧版没有）。
- 慢网络、手机。所有浏览器数字都是本机、不限速测的。
